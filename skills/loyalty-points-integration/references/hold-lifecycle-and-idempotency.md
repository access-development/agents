# Hold Lifecycle and Idempotency

This document covers the business rules for the hold/redeem/refund lifecycle and the idempotency requirements that Access expects your implementation to follow.

---

## Hold Lifecycle

### State Diagram

```
    ┌─────────┐     POST /holds      ┌─────────┐
    │ (none)  │ ──────────────────▶ │ ACTIVE  │
    └─────────┘                     └────┬────┘
                                         │
                    ┌────────────────────┼────────────────────┐
                    │                    │                    │
              POST /redemptions   POST /holds/{id}/cancel   (auto-expire
                    │                    │                  after duration)
                    ▼                    ▼                    │
              ┌─────────┐          ┌──────────┐              ▼
              │ REDEEMED│          │CANCELLED │         ┌─────────┐
              └────┬────┘          └──────────┘         │ EXPIRED │
                   │                                     └─────────┘
              POST /refunds
                   │
                   ▼
              ┌──────────┐
              │ REFUNDED │  (points credited back, original redemption reversed)
              └──────────┘
```

### Hold States

| State | Points Effect | Description |
|-------|--------------|-------------|
| `ACTIVE` | Reserved (deducted from available, not yet permanent) | Hold is in place, points are set aside |
| `EXPIRED` | Restored to available | Auto-released after `hold_duration_minutes` without redemption |
| `CANCELLED` | Restored to available | Explicitly cancelled by Access via cancel endpoint |
| `REDEEMED` | Permanently deducted | Converted to a permanent deduction via redemption endpoint |

### Key Rules

1. **Hold duration**: Access standard is 5 minutes (`hold_duration_minutes: 5`). Your system must auto-release unredeemed holds after expiry. Implement this with:
   - Scheduled jobs (e.g., scan every 10 seconds for expired holds)
   - Database TTLs
   - Timer-based callbacks
   - Whatever mechanism fits your infrastructure

2. **Points are reserved at hold time, not at redemption time**: When a hold is created, the points should be immediately deducted from the member's available balance. The `available_points` returned by the balance endpoint should reflect held points as unavailable. Redemption then converts the reservation to a permanent deduction. Cancel/expire restores the points.

3. **Redemption requires an ACTIVE hold**: You cannot redeem without a prior hold. If the hold has expired or been cancelled, return `HOLD_NOT_FOUND` or `ALREADY_PROCESSED`.

4. **Cancel vs Refund are distinct operations**:
   - **Cancel** (`POST /holds/{id}/cancel`): The hold was only reserved, never redeemed. Points are restored. No billing impact. No revenue share reversal.
   - **Refund** (`POST /refunds`): The hold was already redeemed (points permanently deducted). Points are credited back. This reverses the billing and revenue share for the original transaction.

5. **Atomicity**: Use database transactions for hold creation and redemption to prevent double-spending under concurrent requests. A hold request should atomically: (a) check available balance, (b) deduct points, (c) create hold record. If any step fails, roll back.

6. **Already redeemed holds cannot be cancelled**: If Access calls cancel on a redeemed hold, return `ALREADY_PROCESSED`. The correct way to reverse a redemption is a refund.

### Hold Expiration Implementation Patterns

**Pattern 1: Scheduled job (recommended for most stacks)**
```
Every 10 seconds:
  SELECT holds WHERE status = 'ACTIVE' AND expires_at < NOW()
  FOR EACH hold:
    BEGIN TRANSACTION
    UPDATE hold SET status = 'EXPIRED'
    UPDATE member SET available_points = available_points + hold.points_held
    COMMIT
```

**Pattern 2: Database TTL (if your database supports it)**
- Use Redis with TTL keys that trigger expiration events
- Use PostgreSQL with scheduled pg_cron jobs
- Use MongoDB with TTL indexes

**Pattern 3: Timer-based (for small scale or testing)**
- Start a timer when the hold is created
- On timer fire, check if the hold is still ACTIVE and expire it
- Less reliable under restarts - combine with a scheduled job as a safety net

## Idempotency

### What It Is

All POST endpoints receive an `Idempotency-Key` header from Access. This key is:
- Generated by Access per logical operation (not per HTTP request)
- Stable across retries of the same operation
- Unique across different operations

If Access sends the same `Idempotency-Key` again (e.g., due to a network timeout and retry), your server must return the original response without re-executing the operation.

This follows the [Stripe idempotency convention](https://docs.stripe.com/api/idempotent_requests).

### What You Must Do

1. **Persist the `Idempotency-Key`** with the response for every processed request. Store:
   - The key itself
   - The endpoint it was used on
   - The full response body
   - The HTTP status code
   - The timestamp

2. **On receiving a duplicate key**, return the stored original response:
   - Same status code (200 or 201, not a new 409)
   - Same response body
   - Do not re-execute the operation (do not create a second hold, do not deduct points again)
   - Do **not** return `409 ALREADY_PROCESSED` for that retry. `ALREADY_PROCESSED` is for a *different* operation against a hold that is already `REDEEMED` or `CANCELLED` (for example cancel after a successful redeem). Access treats any 409 as a failed capture and will auto-void other tenders.

3. **Use a persistent store** - whatever fits your stack:
   - Redis (natural fit; set TTL to 48 hours, not to the hold duration)
   - Database table (`idempotency_keys` table with key, response, timestamp)
   - Any durable storage that survives restarts

### Implementation Patterns

**Pattern 1: Redis (recommended)**

```
# On receiving a POST with Idempotency-Key:
cached = redis.get("idempotency:" + key)
if cached:
    return cached.response  # Return original response, do not re-execute

# Process the request...
result = createHold(request)

# Store the response
redis.set("idempotency:" + key, serialize(result), TTL=172800)  # 48 hours, matching Access
return result
```

**Pattern 2: Database table**

```sql
CREATE TABLE idempotency_keys (
  key VARCHAR(255) PRIMARY KEY,
  endpoint VARCHAR(100) NOT NULL,
  response_body TEXT NOT NULL,
  status_code INTEGER NOT NULL,
  created_at TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- On receiving a request:
SELECT * FROM idempotency_keys WHERE key = ?;
-- If found, return stored response.
-- If not found, process request, then INSERT.
```

**Pattern 3: Database transaction with hold record**

If you store holds in a database, you can use the `Idempotency-Key` as a unique constraint on the holds table:

```sql
CREATE TABLE holds (
  idempotency_key VARCHAR(255) UNIQUE,
  hold_id VARCHAR(255) PRIMARY KEY,
  member_key VARCHAR(255) NOT NULL,
  points_held INTEGER NOT NULL,
  status VARCHAR(20) NOT NULL,
  expires_at TIMESTAMPTZ NOT NULL,
  ...
);

-- On receiving a create hold request:
BEGIN;
INSERT INTO holds (idempotency_key, ...) VALUES (?, ...);
-- If unique constraint violation, SELECT existing hold and return it.
-- Otherwise, proceed with balance check and point reservation.
COMMIT;
```

### Edge Cases

- **Key collision across endpoints**: The same `Idempotency-Key` should not be reused across different operations (Access guarantees this). However, defensively, you can scope your idempotency store by endpoint: `idempotency:holds:{key}` vs `idempotency:refunds:{key}`.

- **Concurrent duplicate requests**: If two identical requests arrive simultaneously (before the first one completes), use a lock or database transaction to ensure only one is processed. The second should wait and then return the stored response.

- **TTL for idempotency records**: **Keep idempotency records for at least 48 hours on all operations.** Access retains its own keys for 48 hours, so a shorter TTL on your side creates a window where Access still considers an operation deduplicated but your server no longer does, and would reprocess it. Refunds in particular can arrive days after the original redemption, so err longer rather than shorter. A 1-hour TTL covers the immediate retry burst but not this failure mode.

- **Partial failures**: If your server processes the request but crashes before sending the response, Access will retry with the same key. Your server should detect the stored key and return the stored response (even if the original response was never sent). This is why persisting the response before returning it matters.

## Complete Transaction Flow Example

```
1. User starts session
   Access → GET /v1/loyalty/balance?member_key=abc123
   ← 200: { available_points: 250000, exchange_rate: "0.01", ... }

2. User browses hotels, selects one, proceeds to checkout
   Access → GET /v1/loyalty/balance?member_key=abc123  (re-verify balance)
   ← 200: { available_points: 250000, ... }

3. User chooses to pay with 10,000 points
   Access → POST /v1/loyalty/holds
     Idempotency-Key: "hold-op-001"
     Body: { member_key: "abc123", points_requested: 10000, hold_duration_minutes: 5, ... }
   ← 201: { hold_id: "h-123", status: "ACTIVE", expires_at: "2024-01-15T12:05:00Z", ... }
   (Member's available balance is now 240,000)

4. Access confirms booking with supplier
   Access → POST /v1/loyalty/redemptions
     Idempotency-Key: "redeem-op-001"
     Body: { hold_id: "h-123", member_key: "abc123", points_to_redeem: 10000,
             transaction_details: { transaction_id: "txn-98765", type: "HOTEL_BOOKING", ... } }
     If a confirmatory field is omitted, resolve member_key and the points amount
     from the stored hold rather than rejecting the request.
     See references/endpoint-contract-reference.md, "Redeem Points".
   ← 200: { status: "SUCCESS", points_redeemed: 10000, new_balance: 240000, ... }
   (Hold h-123 is now REDEEMED, points permanently deducted)

5a. User cancels booking BEFORE redemption
   (Hold is still ACTIVE, points only reserved)
   Access → POST /v1/loyalty/holds/h-123/cancel
     Idempotency-Key: "cancel-op-001"
     Body: { reason: "User abandoned checkout" }
   ← 200: { status: "CANCELLED", ... }
   (Points restored to 250,000, no billing impact)

5b. User cancels booking AFTER redemption
   (Hold was REDEEMED, points permanently deducted)
   Access → POST /v1/loyalty/refunds
     Idempotency-Key: "refund-op-001"
     Body: { original_transaction_id: "txn-98765", refund_points: 10000, reason: "Booking canceled" }
   ← 200: { status: "REFUNDED", points_refunded: 10000, new_balance: 250000, ... }
   (Points credited back, billing reversed)

6. Access re-queries balance to update display
   Access → GET /v1/loyalty/balance?member_key=abc123
   ← 200: { available_points: 250000, ... }
```

### Network Timeout and Retry Scenario

```
1. Access → POST /v1/loyalty/holds
     Idempotency-Key: "hold-op-001"
     Body: { member_key: "abc123", points_requested: 10000, ... }

2. Your server processes the request, creates hold "h-123", persists response.
   But the network response is lost (timeout).

3. Access retries with the SAME Idempotency-Key:
   Access → POST /v1/loyalty/holds
     Idempotency-Key: "hold-op-001"   ← same key
     Body: { member_key: "abc123", points_requested: 10000, ... }

4. Your server detects the duplicate key, returns the original response:
   ← 201: { hold_id: "h-123", status: "ACTIVE", ... }   ← same response, no new hold created
```
