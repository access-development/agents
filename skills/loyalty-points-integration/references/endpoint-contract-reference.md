# Endpoint Contract Reference

This document provides detailed schemas, request/response examples, and error codes for all five Loyalty Points API endpoints. The OpenAPI spec (`openapi.yaml`) is the source of truth; this document is a developer-friendly reference with implementation notes.

## Conventions

- **JSON field names**: snake_case (e.g., `member_key`, `points_requested`)
- **Points**: integers, no fractions (e.g., `250000`, not `250000.5`)
- **USD values**: strings with 2 decimal places (e.g., `"0.01"`, `"100.00"`). Pattern: `^\d+\.\d{2}$`
- **Timestamps**: ISO 8601 in UTC (e.g., `2024-01-15T12:00:00Z`)
- **Content-Type**: `application/json` on all requests and responses

## 1. Get Loyalty Balance

`GET /v1/loyalty/balance?member_key={member_key}`

Access calls this at session start, during browsing, and at checkout to get the current balance.

### Request

| Parameter | Location | Required | Description |
|-----------|----------|----------|-------------|
| `member_key` | query | Yes | Globally unique member identifier from the Access Travel SDK |
| `program-key` | header | Not yet sent | Planned for multi-program clients; do not require it (see [program-key](#program-key)) |
| `X-Request-ID` | header | No | Optional correlation/audit identifier |
| `X-Request-Timestamp` | header | Yes | ISO 8601 UTC timestamp from Access |

### Response (200)

```json
{
  "member_key": "abc123",
  "available_points": 250000,
  "loyalty_point_to_usd_exchange_rate": "0.01",
  "max_redemption_usd": "2500.00",
  "timestamp": "2024-01-15T12:00:00Z"
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `member_key` | string | Yes | Echo of the member identifier |
| `available_points` | integer | Yes | Current available points balance |
| `loyalty_point_to_usd_exchange_rate` | string | Yes | Value of one point in USD (e.g., `"0.01"` = 1 point = $0.01). Pattern: `^\d+\.\d{2}$` |
| `max_redemption_usd` | string | No | Maximum USD redeemable in a single transaction. Pattern: `^\d+\.\d{2}$` |
| `timestamp` | string (date-time) | Yes | ISO 8601 UTC timestamp of response generation |

### Response Headers

| Header | Required | Description |
|--------|----------|-------------|
| `X-Response-Timestamp` | Yes | ISO 8601 UTC timestamp generated by your server |

### Error Responses

| Status | `error_code` | When |
|--------|-------------|------|
| 400 | `INVALID_REQUEST` | Missing or invalid `member_key` |
| 404 | `MEMBER_NOT_FOUND` | `member_key` does not match any member |
| 500 | `ERROR` | Internal server error |

### Implementation Notes

- Access calls balance at least twice per session: once at session start and once at checkout. Your response should reflect real-time data, not cached.
- The `loyalty_point_to_usd_exchange_rate` is used by Access to display points-equivalent prices during browsing and to calculate point amounts at checkout. If your exchange rate changes, it takes effect on the next balance call.
- `max_redemption_usd` is optional. If omitted, Access assumes no maximum.

## 2. Create Point Hold

`POST /v1/loyalty/holds`

Reserves points for a pending transaction. Called when the user selects points as payment during checkout.

### Request

| Header | Required | Description |
|--------|----------|-------------|
| `Idempotency-Key` | Yes | Stable across retries; persist for dedup |
| `program-key` | Not yet sent | Planned for multi-program clients; do not require it |
| `X-Request-ID` | No | Optional correlation/audit identifier |
| `X-Request-Timestamp` | Yes | ISO 8601 UTC timestamp from Access |

```json
{
  "member_key": "abc123",
  "points_requested": 10000,
  "hold_duration_minutes": 5,
  "transaction_description": "Hotel booking hold"
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `member_key` | string | Yes | Member identifier |
| `points_requested` | integer | Yes | Points to reserve. Min: 1, Max: 1000000 |
| `hold_duration_minutes` | integer | Yes | Minutes before auto-expiry. Access standard: 5 |
| `transaction_description` | string | Yes | Description of intended transaction. Max: 255 chars |

### Response (201)

```json
{
  "hold_id": "hold-12345",
  "idempotency_key": "ref-abc",
  "points_held": 10000,
  "expires_at": "2024-01-15T12:05:00Z",
  "status": "ACTIVE",
  "timestamp": "2024-01-15T12:00:00Z"
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `hold_id` | string | Yes | Unique identifier for the hold. You generate this. |
| `idempotency_key` | string | Yes | Echo of the `Idempotency-Key` header |
| `points_held` | integer | Yes | Points reserved |
| `expires_at` | string (date-time) | Yes | When the hold auto-expires |
| `status` | string (enum) | Yes | `ACTIVE` (see [hold lifecycle](#hold-status-values)) |
| `timestamp` | string (date-time) | Yes | ISO 8601 UTC timestamp |

### Error Responses

| Status | `error_code` | When |
|--------|-------------|------|
| 400 | `INVALID_REQUEST` | Invalid `points_requested`, missing required fields, or unknown `member_key` |
| 409 | `INSUFFICIENT_POINTS` | Available points < `points_requested` |
| 500 | `ERROR` | Internal server error |

This operation defines only 400, 409, and 500. There is no 404 on hold creation: if `member_key` is unknown, return 400 `INVALID_REQUEST`.

### Implementation Notes

- **Atomicity**: Check balance and reserve points in a single database transaction to prevent double-spending under concurrent requests.
- **Hold duration**: Access standard is 5 minutes. Your system must release unredeemed holds after `expires_at`. Use scheduled jobs, database TTLs, or timers.
- **Idempotency**: If the same `Idempotency-Key` is received again, return the original response without creating a new hold.

## 3. Redeem Points

`POST /v1/loyalty/redemptions`

Converts an active hold into a permanent point deduction. Called after Access confirms the supplier booking.

### Request

| Header | Required | Description |
|--------|----------|-------------|
| `Idempotency-Key` | Yes | Stable across retries |
| `X-Request-ID` | No | Optional correlation/audit identifier |
| `X-Request-Timestamp` | Yes | ISO 8601 UTC timestamp from Access |

```json
{
  "hold_id": "hold-12345",
  "member_key": "abc123",
  "points_to_redeem": 10000,
  "transaction_details": {
    "transaction_id": "txn-98765",
    "type": "HOTEL_BOOKING",
    "description": "Booking for Example Hotel",
    "supplier_confirmation": "CONF-123",
    "usd_value": "100.00"
  }
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `hold_id` | string | Yes | The hold_id from Create Hold response |
| `member_key` | string | Yes | Member identifier |
| `points_to_redeem` | integer | Yes | Points to deduct. Min: 1, Max: 1000000 |
| `transaction_details` | object | Yes | Transaction metadata |
| `transaction_details.transaction_id` | string | Yes | Access-generated transaction correlation ID |
| `transaction_details.type` | string (enum) | Yes | `HOTEL_BOOKING`, `CAR_RENTAL`, or `TICKET_PURCHASE` |
| `transaction_details.description` | string | Yes | Human-readable description. Max: 255 chars |
| `transaction_details.supplier_confirmation` | string | No | Supplier booking confirmation (recommended for refund reconciliation) |
| `transaction_details.usd_value` | string | Yes | USD value of points redeemed. Pattern: `^\d+\.\d{2}$` |

### Response (200)

```json
{
  "status": "SUCCESS",
  "transaction_id": "txn-98765",
  "hold_id": "hold-12345",
  "points_redeemed": 10000,
  "new_balance": 240000,
  "timestamp": "2024-01-15T12:00:00Z",
  "idempotency_key": "ref-abc"
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `status` | string (enum) | Yes | `SUCCESS` or `FAILED` |
| `transaction_id` | string | Yes | Echo of transaction_id from request |
| `hold_id` | string | Yes | Echo of hold_id from request |
| `points_redeemed` | integer | Yes | Actual points deducted |
| `new_balance` | integer | No | Member's available points after redemption |
| `timestamp` | string (date-time) | Yes | ISO 8601 UTC timestamp |
| `idempotency_key` | string | Yes | Echo of `Idempotency-Key` header |

### Error Responses

| Status | `error_code` | When |
|--------|-------------|------|
| 400 | `INVALID_REQUEST` | Invalid `hold_id` format, or body fields that contradict the stored hold |
| 409 | `HOLD_NOT_FOUND` | Hold does not exist or has expired |
| 409 | `ALREADY_PROCESSED` | Hold has already been redeemed or cancelled |
| 500 | `ERROR` | Internal server error |

Redemptions define **no 404**. `HOLD_NOT_FOUND` is returned as **409** here, unlike the cancel endpoint where it is 404.

### Implementation Notes

- **Verify the hold is ACTIVE** before deducting. If the hold has expired or been cancelled, return `HOLD_NOT_FOUND` or `ALREADY_PROCESSED`.
- **Atomic deduction**: Deduct points and update ledger in a single transaction.
- **Store the transaction_id**: You will need it to match refund requests later.
- **`supplier_confirmation`** is optional but recommended - it helps with refund reconciliation.

> **Important: do not hard-fail on missing body fields.**
>
> The spec marks `member_key`, `points_to_redeem`, and `transaction_details` as required, but Access does not currently populate them on every redemption. Some requests arrive carrying only `hold_id`:

```json
{ "hold_id": "hold-12345" }
```

> If you reject these with 400 `INVALID_REQUEST`, redemptions will fail in production even though your implementation matches the written contract.
>
> **Resolve what you need from the stored hold instead.** You created the hold, so you already hold the authoritative `member_key` and points amount. Treat the body fields as confirmatory when present and as absent-but-recoverable when not:
>
> 1. Look up the hold by `hold_id`. If it does not exist, that is a genuine `HOLD_NOT_FOUND`.
> 2. Take `member_key` and the points amount from the hold record.
> 3. If the request *does* carry `member_key` or `points_to_redeem`, cross-check them against the hold and reject on mismatch. A mismatch is a real error; an omission is not.
> 4. Treat `transaction_details` as optional metadata. Persist it when present. If absent, generate your own internal transaction identifier and return it as `transaction_id`, since Access uses that value as `original_transaction_id` on any later refund.
>
> This is tracked as a defect against the Access caller. Build defensively until it is resolved.

## 4. Refund Points

`POST /v1/loyalty/refunds`

Credits points back to a member after a cancellation or refund. Called after Access processes the member refund and receives supplier cancellation confirmation.

### Request

| Header | Required | Description |
|--------|----------|-------------|
| `Idempotency-Key` | Yes | Stable across retries |
| `X-Request-ID` | No | Optional correlation/audit identifier |
| `X-Request-Timestamp` | Yes | ISO 8601 UTC timestamp from Access |

```json
{
  "original_transaction_id": "txn-98765",
  "refund_points": 10000,
  "reason": "Booking canceled"
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `original_transaction_id` | string | Yes | The `transaction_id` from the original Redeem response |
| `refund_points` | integer | Yes | Points to credit back. Min: 1, Max: 1000000 |
| `reason` | string | Yes | Human-readable reason. Max: 255 chars |

### Response (200)

```json
{
  "status": "REFUNDED",
  "refund_id": "REF-2024-11223",
  "original_transaction_id": "txn-98765",
  "points_refunded": 10000,
  "new_balance": 250000,
  "timestamp": "2024-01-15T12:00:00Z",
  "idempotency_key": "ref-abc"
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `status` | string (enum) | Yes | `REFUNDED` or `FAILED` |
| `refund_id` | string | No | Unique ID for this refund |
| `original_transaction_id` | string | Yes | Echo of original_transaction_id from request |
| `points_refunded` | integer | Yes | Actual points credited back |
| `new_balance` | integer | No | Member's available points after refund |
| `timestamp` | string (date-time) | Yes | ISO 8601 UTC timestamp |
| `idempotency_key` | string | Yes | Echo of `Idempotency-Key` header |

### Error Responses

| Status | `error_code` | When |
|--------|-------------|------|
| 400 | `INVALID_REQUEST` | Missing required fields |
| 409 | `ALREADY_PROCESSED` | Refund already processed for this transaction/idempotency key |
| 500 | `ERROR` | Internal server error |

### Implementation Notes

- **Refund vs Cancel**: Refund is for points that were already redeemed (deducted). Cancel is for holds that were never redeemed. These are distinct operations.
- **Partial refunds**: `refund_points` may be less than the original redemption amount. Your system should support partial refunds.
- **Look up by `original_transaction_id`**: You must store the `transaction_id` from the Redeem endpoint to match refund requests.

## 5. Cancel Point Hold

`POST /v1/loyalty/holds/{hold_id}/cancel`

Releases a hold without redeeming. Points were only reserved, never deducted. No billing impact.

### Request

| Header | Required | Description |
|--------|----------|-------------|
| `Idempotency-Key` | Yes | Stable across retries |
| `X-Request-ID` | No | Optional correlation/audit identifier |
| `X-Request-Timestamp` | Yes | ISO 8601 UTC timestamp from Access |

| Parameter | Location | Required | Description |
|-----------|----------|----------|-------------|
| `hold_id` | path | Yes | The hold_id to cancel |

```json
{
  "reason": "User abandoned checkout"
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `reason` | string | No | Reason for cancellation. Max: 255 chars |

### Response (200)

```json
{
  "status": "CANCELLED",
  "timestamp": "2024-01-15T12:00:00Z",
  "idempotency_key": "ref-abc"
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `status` | string (enum) | Yes | `CANCELLED` or `FAILED` |
| `timestamp` | string (date-time) | Yes | ISO 8601 UTC timestamp |
| `idempotency_key` | string | Yes | Echo of `Idempotency-Key` header |

### Error Responses

| Status | `error_code` | When |
|--------|-------------|------|
| 400 | `INVALID_REQUEST` | Invalid hold_id format |
| 404 | `HOLD_NOT_FOUND` | Hold does not exist |
| 409 | `ALREADY_PROCESSED` | Hold already redeemed or cancelled |
| 500 | `ERROR` | Internal server error |

### Implementation Notes

- **Restore points**: When cancelling, restore the held points to the member's available balance.
- **Cancel vs auto-expire**: Both result in the hold being released. Cancel is explicit (Access calls the endpoint). Auto-expire is your system's internal mechanism after `expires_at`.
- **Already redeemed holds cannot be cancelled**: If the hold has been redeemed, return `ALREADY_PROCESSED`. The correct operation for reversing a redemption is a refund, not a cancel.

## program-key

> **Access does not currently send `program-key`.** It is documented here as planned behavior so multi-program clients can design for it. Your server must not require it, and must not reject a request that omits it.

The header is planned for the **balance** and **holds** endpoints only. It is not planned for redemption, refund, or cancel, because those reference existing holds or transactions that already encode the program context.

### How to handle it today

- **Do not require it.** Every request Access sends today omits it. Requiring it breaks the whole integration.
- **Read it if present, fall back if absent.** Resolve to your single configured program when the header is missing.
- **Do not branch business logic on it** until Access confirms it is live.

### When it would matter

`program-key` becomes relevant when a single API server handles multiple loyalty program instances with Access:

- **Multiple subscription tiers**: A client has one program for hotels-only and another for hotels + theme parks. Each tier is a separate program with Access, billed independently.
- **Multiple brands**: A client operates multiple brands or divisions, each with its own loyalty program managed by Access.
- **Shared infrastructure**: A single API server serves multiple Access programs for efficiency.

Most clients have a single program with Access. If you have one `member_key` space, one points pool, and one exchange rate, this does not apply to you.

### If you are unsure

If you think you need multi-program support, raise it with your Access Implementation Manager rather than building against this header.

## Error Response Schema

All error responses use this shape:

```json
{
  "error_code": "INSUFFICIENT_POINTS",
  "message": "Member has 500 points; requested 10000",
  "details": {
    "available_points": 500,
    "requested_points": 10000
  }
}
```

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `error_code` | string (enum) | Yes | Machine-readable error code |
| `message` | string | Yes | Human-readable error message |
| `details` | object | No | Additional context (free-form key-value pairs) |

### Error Codes

The HTTP status is per-operation, because each operation declares its own response set. There is no single global mapping.

| Code | HTTP Status | Valid on | Description |
|------|-------------|----------|-------------|
| `INVALID_REQUEST` | 400 | All | Validation failure |
| `INSUFFICIENT_POINTS` | 409 | Holds | Available points < requested points |
| `HOLD_NOT_FOUND` | **404** | Cancel | Hold ID does not exist |
| `HOLD_NOT_FOUND` | **409** | Redemptions | Hold does not exist or has expired (redemptions declare no 404) |
| `MEMBER_NOT_FOUND` | 404 | Balance | `member_key` does not match any member |
| `ALREADY_PROCESSED` | 409 | Redemptions, refunds, cancel | Operation already completed for this resource or idempotency key |
| `ERROR` | 500 | All | Internal server error |

Responses declared per operation, for reference:

| Operation | Declared statuses |
|---|---|
| `GET /v1/loyalty/balance` | 200, 400, 404, 500 |
| `POST /v1/loyalty/holds` | 201, 400, 409, 500 |
| `POST /v1/loyalty/redemptions` | 200, 400, 409, 500 |
| `POST /v1/loyalty/refunds` | 200, 400, 409, 500 |
| `POST /v1/loyalty/holds/{hold_id}/cancel` | 200, 400, 404, 409, 500 |
